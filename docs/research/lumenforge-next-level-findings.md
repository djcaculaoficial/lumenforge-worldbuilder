# Lumenforge Next-Level Feature Study — Research Notes

## Initial Findings

| Source | Relevant evidence | Product implication for Lumenforge |
| --- | --- | --- |
| [Yarn Spinner](https://yarnspinner.dev/) | Its public positioning centers on planning, writing, integrating, and testing dialogue, alongside live validation, syntax assistance, and readable branching language. | Lumenforge should mature from a simple node editor into an authored narrative pipeline with validation, test transcripts, writer ergonomics, and a runtime integration boundary. |
| [Adventure Creator](https://adventurecreator.org/) | Its feature overview combines hotspots, visual actions, inventory, dialogue, logic, localization, save/load, cutscenes, timeline integration, and an extension API. | The next-level roadmap must treat scenario interaction, state, cinematics, accessibility, localization, QA, and extensibility as one connected authoring system rather than isolated panels. |
| [GDevelop Events documentation](https://wiki.gdevelop.io/gdevelop5/events/) | The event model is built around conditions and actions, and its documentation covers sub-events, object selection, loops, groups, links, JavaScript code, and custom functions. | Lumenforge should expand its current blocks into scoped, reusable event sheets with explicit trigger/condition/action semantics, while retaining Lua as an advanced escape hatch. |
| [Godot animation documentation](https://docs.godotengine.org/en/stable/tutorials/animation/introduction.html) | The animation system foregrounds timeline playback, animation tracks, reusable libraries, blending, and markers. | Lumenforge cutscenes should evolve from ordered shots into multi-track sequence assets with camera, actor, audio, property, event, and subtitle tracks, plus reusable sequence libraries. |
| [Twine accessibility guidance](https://twinery.org/accessibility-and-compliance/) | Twine describes accessibility as a core design goal, uses WCAG-informed implementation, and runs automated Axe coverage. | Lumenforge needs creator-side accessibility linting and project-side accessibility presets, rather than treating captions and reduced motion as late export options. |
| [Ink repository and architecture overview](https://github.com/inkle/ink) | Ink is explicitly structured as an interactive-narrative language with a compiler, runtime, command-line tooling, and test-oriented source layout. | Lumenforge should separate its editable narrative and behaviour model from a deterministic compiled runtime, including source maps, tracebacks, tests, and reproducible game builds. |
| [Yarn Spinner localisation and assets](https://docs.yarnspinner.dev/yarn-spinner-for-unity/assets-and-localization) | Its workflow uses stable line IDs, CSV string export/import, translated string tables, and locale-specific assets such as voice audio. | Lumenforge should make stable content IDs first-class, then add a translation workbench, CSV/XLIFF exchange, missing-translation checks, and voice/subtitle asset mapping. |
| [GDevelop debugger and profiler](https://wiki.gdevelop.io/gdevelop5/interface/debugger/) | Its runtime tools inspect scenes, object instances, global and scene variables, permit controlled edits, and profile game execution. | Lumenforge needs a play-in-editor debugger with a state ledger, interaction trace, breakpoints, controlled variable overrides, and per-sequence performance diagnostics. |

## Working Design Criteria

The study will favour features that keep Lumenforge **local-first**, approachable to non-programmers, capable of gradual Lua escalation, and specific to cinematic 2D narrative adventures. Features will be marked foundational only when they unlock several later systems, not merely because they are fashionable in general-purpose engines.
